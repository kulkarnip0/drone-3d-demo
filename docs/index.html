Drone Autonomy Architecture Vision

This page explains the intended architecture behind the drone demo: a browser GCS, a drone companion computer, a safety-critical flight controller, mission-specific edge foundation models, realistic 3D environments, and friendly / unknown / enemy asset reasoning.

1. Vision: putting intelligence on the edge

The core idea is not only to make a 3D code demo. The larger idea is to train or adapt a mission-specific foundation model and place it on the drone companion computer / edge device. The GCS gives intent. The edge model understands the local scene and mission context. The flight controller executes safe low-level motion. 

Mission intent from GCS
        ↓
Mission-specific foundation model on companion computer
        ↓
Scene understanding + belief state + task decision
        ↓
MAVLink commands / waypoints / inspection tasks
        ↓
ArduPilot flight controller
        ↓
Motors, sensors, safe flight execution
Key principle: the foundation model should not directly spin motors. It should reason about scene, mission, risks and tasks. The flight controller remains responsible for stabilization, failsafes, arming checks, landing, RTL and safe low-level control.

3. Drone component showcase

A real drone autonomy stack is easier to understand when the physical drone is mapped to software roles.

Flight controller

Safety-critical autopilot

Runs ArduPilot/PX4-like logic: stabilization, modes, EKF, failsafes, LAND/RTL and motor mixing.

Companion computer

Edge autonomy

Runs perception, mission-specific foundation model, local planning, and communicates with the flight controller using MAVLink.

Sensors

Scene input

Camera, GPS, IMU, barometer, range sensor or LiDAR provide raw observations for state estimation and scene understanding.

Communication

GCS link

Telemetry and mission commands move between GCS and vehicle through MAVLink over radio, Wi-Fi, LTE or mesh networking.

4. Mission-specific foundation model on the edge

The foundation model is the semantic brain of the drone. It is trained, fine-tuned, distilled or adapted for the mission domain: road inspection, perimeter surveillance, disaster response, search-and-rescue, swarm coordination, or asset classification. 

Generic foundation model
        ↓ fine-tune / distill / specialize
Mission-specific edge model
        ↓
Understands local scene:
  road, vehicle, human, tree, building, open area, obstacle
        ↓
Understands mission context:
  friendly asset, unknown asset, enemy asset, no-fly zone, priority zone
        ↓
Outputs structured belief state and recommended next action
semantic segmentation object detection depth / 3D reasoning asset classification mission reasoning uncertainty tracking

The aerial intersection image is useful as a mental model for what a drone camera sees: road geometry, vehicles, buildings, vegetation, parking spaces and possible mission-relevant assets.

The edge model should convert such raw imagery into semantic layers: road, lane, junction, parked vehicle, moving vehicle, building, tree, open area, obstacle, safe landing area and mission-relevant asset.

6. Belief state from the drone

A drone should not only say “I see pixels.” It should maintain a belief state: what it currently believes about the world, with confidence, uncertainty and mission labels. 

Drone observation
  camera image + pose + altitude + timestamp
        ↓
Edge foundation model
        ↓
Belief state
  static map:
    road corridor: high confidence
    intersection: high confidence
    buildings: medium/high confidence
    trees/vegetation: high confidence
    open/parking area: medium confidence

  dynamic objects:
    vehicles: detected, track confidence 0.70–0.95
    pedestrians: unknown / not visible

  tactical labels:
    friendly asset: known blue icon / confirmed ID
    unknown asset: detected but not classified
    enemy asset: only if mission rules and evidence support it

  uncertainty:
    occluded region behind trees/buildings
    low-confidence detections near shadows

  recommended next action:
    inspect intersection
    orbit target area
    request GCS confirmation
    send waypoint to flight controller

8. Roadmap: from demo to realistic autonomy

Step 1

Browser 3D environment

Build roads, buildings, trees, friendly assets, unknown assets and enemy assets in a web-based 3D scene.

Step 2

GCS dashboard

Visualize drone state, mission intent, map, detections, belief state and operator approvals.

Step 3

ArduPilot / Gazebo backend

Connect the web GCS to the SITL backend using WebSocket/REST, and map live MAVLink state into the 3D view.

Step 4

Edge model

Run mission-specific model on companion computer; send high-level commands to the flight controller, not direct motor control.
