1. What this project is trying to help visualize

The goal is not only to show a few animated drones. The larger goal is to build intuition for a realistic autonomy stack: an operator at a Ground Control Station, one or more UAVs with flight controllers, onboard companion computers, sensor payloads, communication links, mission-level intelligence, and a 3D operational environment containing friendly and adversarial assets.

GCS

Mission command

The operator assigns intent: survey an area, track a target, inspect an asset, hold a perimeter, or return home.

Companion

Onboard autonomy

A Jetson/Raspberry Pi/NUC-style computer runs local-agent logic, perception, object detection, and future foundation-model reasoning.

Flight controller

Safe control

Pixhawk/Cube/ArduPilot handles arming, EKF, modes, failsafes, stabilization, and motor outputs.

3D world

Operational context

The environment contains terrain, buildings, paths, vehicles, friendly units, enemy units, sensors, and map-building tools.

2. Real-world architecture

In real hardware, the AI planner should not directly control motors. It should send high-level commands to a flight controller through MAVLink.

                 ┌──────────────────────────────┐
                 │ Ground Control Station / GCS  │
                 │ mission planning, monitoring  │
                 │ operator decisions, map UI    │
                 └──────────────┬───────────────┘
                                │ secure radio / Wi-Fi / LTE / mesh
                                │ high-level mission goals
                                ▼
        ┌─────────────────────────────────────────────────┐
        │ UAV onboard companion computer                   │
        │ Jetson / Raspberry Pi / NUC                      │
        │                                                 │
        │ local-agent  +  perception  +  AI reasoning      │
        │ YOLO / tracking / VLM / tactical assistant       │
        └──────────────┬──────────────────────────────────┘
                       │ MAVLink over USB / UART / UDP
                       ▼
        ┌─────────────────────────────────────────────────┐
        │ Flight controller                               │
        │ Pixhawk / Cube running ArduPilot                 │
        │                                                 │
        │ EKF, arming, modes, failsafes, motor control     │
        └──────────────┬──────────────────────────────────┘
                       │ PWM / DShot / actuator outputs
                       ▼
                 ┌─────────────┐
                 │ Drone body  │
                 │ motors, ESC │
                 │ sensors     │
                 └─────────────┘
Design rule: the companion computer decides what should be done; ArduPilot decides how to fly safely.

4. Communication and networking picture

The system has different communication layers. Keeping them separate makes the architecture easier to debug.

MAVLink

Companion ↔ flight controller

Heartbeat, mode change, arm/disarm, telemetry, mission commands, guided setpoints, command ACK.

Swarm link

GCS ↔ UAVs

Mission assignment, swarm health, role changes, target reports, emergency actions.

Web state

Backend ↔ browser

Drone pose, paths, detections, alerts, map edits, asset state. Good future fit: WebSocket.

Simulator link

SITL ↔ Gazebo

Motor outputs and simulated sensor/physics state. This is not the same as MAVLink.

   │
   ├── WebSocket/REST: visualization state, commands, map edits
   │
Mission backend / bridge
   │
   ├── MAVLink UDP: telemetry and high-level commands
   │
Companion computer or agent
   │
   ├── MAVLink USB/UART/UDP
   │
Flight controller / ArduPilot

5. AI and foundation-model layer

Foundation models should not be placed in the low-level flight-control loop. They are better used for semantic understanding, mission reasoning, report generation, and operator assistance.

On companion computer

Local autonomy and perception

  • YOLO / RT-DETR object detection from drone camera.
  • Tracking of vehicles, persons, friendly units, and suspicious objects.
  • Lightweight VLM for scene understanding on Jetson-class hardware.
  • Local safety rules: land, hold, avoid, report, return.
At GCS or mission server

Higher-level reasoning

  • Natural-language mission planning.
  • Area division among drones.
  • Threat/friendly asset interpretation.
  • Summary: what happened, what was detected, what is risky.

6. 3D environment-building vision

The 3D world should slowly evolve from a simple browser scene into an operational map where assets, sensors, routes, detections, and missions can be placed and replayed.

Terrain

Base world

Ground, roads, buildings, landing zones, restricted areas, safe corridors.

Map builder

Editable scene

Place objects, draw patrol areas, create waypoints, mark danger regions.

Sensor view

FOV and coverage

Show drone camera cone, detection zone, blind spots, and overlap between drones.

Mission replay

Timeline

Replay drone paths, detections, commands, failures, and operator decisions.

7. Friendly and enemy asset modelling

A useful demo needs operational meaning. Assets should not be just decorative models; they should carry identity, role, state, intent, and relationship to the mission.

8. Role of this repository

This repository can act as the visual and interaction layer. It does not need to contain all backend autonomy code. Instead, it can become the web-facing interface for understanding and demonstrating the complete drone autonomy system.

Now

Browser demo

3D drone visualization, map building, simple paths, FOV, dashboard, and AI-assist UI.

Next

State-driven frontend

Accept live JSON state from a backend: drone poses, detections, missions, alerts.

Later

Connected GCS

Send operator commands to a backend bridge that talks MAVLink to SITL or real vehicles.

Final vision

Autonomy cockpit

Visualize swarm reasoning, foundation-model suggestions, friendly/enemy assets, and mission state.

drone-3d-demo
  = browser GCS + 3D visualization + map/asset editor

ardupilot-swarm-sim
  = Gazebo + ArduPilot SITL + MAVLink + local-agent + companion simulation

Future bridge
  = WebSocket/REST service between both worlds
