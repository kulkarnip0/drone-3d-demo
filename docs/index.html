Drone Autonomy Architecture Vision

A mission-specific autonomy stack where the GCS gives intent, the edge companion computer runs perception and reasoning, the flight controller executes safe low-level control, and a 3D environment helps us design, explain, and test the mission.

1. Core vision

The idea is not only to show a code demo. The larger idea is to build a mental and technical bridge from a browser 3D demo to a real drone autonomy system. A mission-specific foundation model can be fine-tuned or distilled and placed on the drone's companion computer. The model understands scene context, mission rules, friendly assets, unknown assets, possible threats, and tactical intent. The flight controller remains responsible for safe attitude, stabilization, arming, landing, failsafe, and motor control. 

Mission intent from GCS
        ↓
Mission-specific foundation model on companion computer
        ↓
Scene understanding + belief state + task decision
        ↓
MAVLink command to ArduPilot / flight controller
        ↓
Safe low-level flight execution
        ↓
Telemetry + detections + belief update back to GCS

2. Drone component showcase

flight controller

Safety-critical control

Runs ArduPilot/PX4-style logic: estimator, modes, arming, stabilization, failsafes, landing, RTL, and motor outputs.

companion computer

Edge intelligence

Runs mission logic, perception models, foundation-model reasoning, object tracking, route selection, and MAVLink command generation.

motors + ESCs

Physical actuation

Convert flight-controller outputs into thrust. The autonomy stack should never directly bypass the safety controller to command motors.

sensors

World observation

Camera, IMU, GPS, barometer, compass, range sensors, and optional depth/LiDAR provide the raw information needed for local belief.

communication

Network link

Radio, Wi-Fi, LTE, mesh, or tactical datalink connects drone, GCS, and swarm peers with varying latency and reliability.

power

Battery budget

The foundation model must respect power, heat, and compute limits. Edge autonomy must be mission-specific, efficient, and safety-aware.

4. Mission-specific foundation model on the edge

A large foundation model may be trained or adapted offline, but the deployed drone needs an efficient mission-specific version: distilled, quantized, or split into perception + reasoning modules. The edge model should not replace the flight controller. It should interpret the scene and decide what mission-level action is useful and safe.

input

What the model sees

Camera image, detections, map context, telemetry, prior mission state, friendly asset locations, no-fly zones, and communication quality.

reasoning

What the model builds

A belief state: road, building, tree, vehicle, open area, unknown object, threat probability, confidence, and next-best viewpoint.

output

What it commands

Inspect area, orbit target, hold position, update map, follow route, request human confirmation, or send waypoint/velocity command.

6. Belief state from the drone

The belief state is the internal scene memory of the drone. It is not just object detection. It combines perception, confidence, mission labels, uncertainty, and recommended next actions. 

belief_state:
  drone:
    pose: [x, y, z, yaw]
    mode: guided / auto / hold
    battery: normal
    link_quality: medium

  static_scene:
    road_corridor: detected, confidence 0.93
    intersection: detected, confidence 0.89
    buildings: detected, confidence 0.86
    trees_vegetation: detected, confidence 0.91
    parking_or_open_area: detected, confidence 0.78

  dynamic_objects:
    vehicles:
      - id: car_01
        location: near_intersection
        motion: slow_or_parked
        confidence: 0.82
      - id: car_02
        location: vertical_road
        motion: unknown
        confidence: 0.74

  tactical_labels:
    friendly_assets: []
    enemy_or_suspicious_assets:
      - candidate_object_near_road_edge
    unknown_assets:
      - partially_occluded_vehicle
      - unclear_object_near_building

  uncertainty:
    occluded_regions:
      - behind_trees
      - building_shadow_area
    next_best_view:
      action: move_to_oblique_viewpoint
      reason: reduce occlusion and verify unknown assets

  recommended_action:
    type: inspect
    target: intersection_and_unknown_assets
    command_to_flight_controller: waypoint_or_orbit_request
This is the core of the architecture: the foundation model creates mission understanding, but the flight controller executes only safe flight commands.

7. Networking and communication

GCS ⇄ Drone companion:
  - mission intent
  - map updates
  - operator commands
  - detection summaries
  - health state

Companion ⇄ Flight controller:
  - MAVLink heartbeat
  - mode changes
  - waypoint / velocity / land / RTL commands
  - telemetry
  - command acknowledgements

Drone ⇄ Drone:
  - peer location
  - local map fragments
  - task allocation
  - warning messages
  - bandwidth-aware summaries

9. Roadmap

phase 1

Explain architecture

Use the web docs to show GCS, companion computer, flight controller, assets, networking, and belief state.

phase 2

Build richer 3D environment

Add terrain, roads, buildings, trees, friendly units, unknown objects, enemy-like assets, and mission zones.

phase 3

Connect simulated state

Stream drone telemetry and mission state from the ArduPilot/Gazebo backend into the browser GCS.

phase 4

Add edge AI loop

Run a mission-specific perception/reasoning model on a companion-computer process and visualize its belief state.
