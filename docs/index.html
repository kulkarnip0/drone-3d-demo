2. Drone components: from picture to autonomy stack

Image source: Wikimedia Commons, Drone Diagram.jpg, author Glosome. Used here as a component reference for learning and architecture explanation.

A quadcopter can be understood as several layers. The physical drone has motors, propellers, frame, battery, camera, sensors, and radio links. The autonomy system adds a flight controller, companion computer, network protocol, mission logic, perception models, and a GCS. 

Physical drone
  frame + arms + propellers + motors + battery

Flight-control layer
  flight controller + IMU + GPS + barometer + RC/MAVLink

Autonomy layer
  companion computer + perception + planning + safety monitor

Operator layer
  GCS + map + telemetry + mission commands
LiftPropellers + motorsConvert motor commands into thrust. The flight controller changes motor speeds to roll, pitch, yaw, climb, descend, and stabilize.
PowerBattery + power boardSupplies energy to motors, flight controller, companion computer, sensors, and communication modules.
ControlFlight controllerRuns ArduPilot/PX4-style control loops, stabilization, estimator, modes, failsafes, and motor mixing.
AutonomyCompanion computerRuns higher-level Python/ROS/AI logic: perception, tracking, mission reasoning, task allocation, and MAVLink commands.
SensingCamera / payload / GPS / IMUProvides measurements for navigation and understanding: pose, altitude, visual detections, object tracking, and map updates.
CommunicationTelemetry radio / Wi-Fi / LTEConnects drone to GCS and swarm peers. Carries heartbeat, telemetry, mission commands, video, and AI summaries.

3. Core system architecture

The clean architecture separates the safety-critical flight controller from the higher-level autonomy logic. The companion computer should not directly drive motors. It should send mission-level commands through MAVLink. 

Human Operator
   │
   ▼
Ground Control Station / GCS
   │  mission, map, tasking, telemetry, video
   │
   ▼
Network Layer
   │  MAVLink / UDP / serial / radio / Wi-Fi / LTE
   │
   ▼
Companion Computer
   │  perception, foundation models, tracking, planning, safety supervisor
   │
   ▼
Flight Controller
   │  ArduPilot modes, EKF, stabilization, failsafes, motor control
   │
   ▼
Drone Hardware
      motors, ESCs, propellers, sensors, camera, battery
Mental model: the flight controller is the safety-critical pilot. The companion computer is the mission brain. The GCS is the human-facing command and visualization layer.

4. Networking and message flow

MAVLink

Command and telemetry language

Used for heartbeat, modes, arm/disarm, position targets, mission commands, status text, battery, GPS, and vehicle state.

UDP / Serial

Transport pipe

In simulation, MAVLink often goes over UDP ports. On real drones, it may go over USB, serial telemetry radio, Wi-Fi, or LTE.

Router

Multi-client distribution

A MAVLink router can forward one vehicle stream to GCS, logger, local agent, and monitoring tools.

Swarm network

Many drones, many links

Each drone needs identity, endpoint, telemetry stream, safety policy, and command permissions.

Simulation example
  GCS / Browser frontend

  Backend bridge
      ↕ MAVLink UDP

  Motors and sensors

5. Foundation models and AI role

Foundation models should not replace the low-level flight controller. They are better used for perception, semantic understanding, mission reasoning, and operator assistance.

LayerWhat AI can doWhat should remain safety-controlled
PerceptionDetect vehicles, humans, buildings, roads, landing zones, obstacles, friendly/enemy assets.Raw motor stabilization and failsafe control.
Semantic mapConvert visual detections into map annotations and object tracks.Estimator and core navigation integrity.
PlanningSuggest search paths, inspection priorities, asset classification, threat avoidance corridors.Geofence, RTL, LAND, collision safety, flight envelope limits.
GCS assistantExplain mission status: “Drone 2 sees unknown vehicle near sector B.”Final safety authority and emergency response.
 
Camera / sensors
   ↓
Perception model
   ↓
Detections + tracks
   ↓
Semantic world model
   ↓
Planner / AI assistant
   ↓
Safe MAVLink commands
   ↓
Flight controller

6. 3D environment building

The browser demo can slowly grow into a mission-design environment. Start simple: place terrain, roads, buildings, friendly assets, unknown objects, enemy assets, and drone paths. Later, connect these objects to live simulation or real-world telemetry.

Terrain

Ground plane, hills, map tiles, roads, landing zones, no-fly zones.

Placeables

Interactive assets

User can place trucks, bases, towers, buildings, markers, obstacles, and mission points.

Drone FOV

Sensor visualization

Show what a drone camera can see and which objects are inside its view cone.

Scenario design

Training and demos

Create “find object”, “inspect convoy”, “protect base”, or “map unknown area” scenarios.

7. Friendly, unknown, and enemy asset model

For a useful demo, every object in the 3D world should have a semantic role. The GCS should not only show shapes; it should show operational meaning. 

Asset types
  FRIENDLY
    own drones, own base, protected vehicles, safe landing zone

  UNKNOWN
    unidentified vehicle, person, temporary structure, new object

  ENEMY / THREAT
    hostile vehicle, jammer, restricted zone, suspected launcher, hostile drone

  NEUTRAL
    civilian vehicle, building, road infrastructure, trees, poles
Friendly

Known safe objects

Rendered with clear identity, health, role, team color, assigned mission, and protection priority.

Unknown

Needs classification

Tracked by the system but not yet classified. Good place for AI-assist and human confirmation.

Enemy / threat

Risk source

Used for route avoidance, alerting, tracking, and mission replanning.

Mission object

Task anchor

Inspection point, waypoint, search grid, relay point, pickup/drop zone, or observation sector.

9. Roadmap from demo to real system

Step 1

Static visual world

Build terrain, drone models, friendly/enemy assets, and camera/FOV visualization.

Step 2

Interactive mission design

Allow operator to create waypoints, place objects, assign asset labels, and simulate detections.

Step 3

Backend bridge

Connect web frontend to a local backend through WebSocket or REST.

Step 4

SITL integration

Stream ArduPilot/Gazebo drone position and status into the web view.

Step 5

AI-assisted perception

Use detections and semantic labels to update the map and explain mission status.

Step 6

Real hardware path

Replace SITL endpoints with real companion computers and flight controllers while keeping the same GCS concept.
