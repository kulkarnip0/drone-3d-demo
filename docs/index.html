Drone 3D Demo Architecture

A web-friendly architecture guide for the drone-3d-demo repository. This project is a browser-based 3D drone visualization, GCS dashboard, map builder, sensor/FOV demo, and state-driven simulation frontend.

1. Big-picture architecture

The repository is mainly a frontend simulation and visualization layer. It is not the real ArduPilot/Gazebo SITL backend. It can later become a web GCS frontend that receives live state from a backend and displays drones, paths, map assets, sensor fields of view, and AI-assist information.

4. Module meaning

core

Viewer and controls

src/core owns the 3D viewer creation and camera controls. This is the foundation used by the demo, GCS, and map builder pages.

drones

Drone fleet

src/drones creates drone objects, builds a fleet, and provides paths that drones can follow inside the browser demo.

sensors

FOV and detection

src/sensors handles drone field-of-view detection and tracks which assets are visible or detected by a drone sensor cone.

gcs

Ground station UI

src/gcs contains the dashboard, minimap, and AI-assist panel. This is the operator-facing part of the demo.

mapBuilder

Map editor

src/mapBuilder is for building or editing the 3D map/world. It works with placeable assets.

state

State bridge

src/state is the future integration point for connecting frontend visualization to a backend simulator or live drone state stream.

5. State and command concept

The clean design is to keep the frontend independent from the real flight controller. The browser should receive high-level state and send high-level commands, not talk directly to motors or ArduPilot internals. 

Frontend GCS / Browser
  receives:
    drone position
    drone heading
    path / mission state
    sensor detections
    health / battery / warning state

  sends:
    start mission
    pause mission
    select drone
    inspect area
    create waypoint
    assign task
Recommended rule: the web demo should remain a visualization and operator layer. Flight-control commands should go through a backend that validates safety and talks MAVLink to ArduPilot.

6. How this can connect to ArduPilot / Gazebo later

Your second repo, ardupilot-swarm-sim, is the better place for Gazebo, ArduPilot SITL, Docker, MAVLink, companion-agent, and planner code. This drone-3d-demo repo can become the web visualization/GCS layer.

7. Suggested next improvements

  • Add a simple WebSocket client in src/state to receive live drone state.
  • Define a JSON state schema for drones, detections, commands, and mission status.
  • Add a backend bridge in ardupilot-swarm-sim that converts MAVLink telemetry to frontend-friendly JSON.
  • Keep browser commands high-level: waypoint, inspect, hold, land, return, not raw throttle.
  • Use the GCS dashboard as the operator view and the map builder as the mission-design view.
