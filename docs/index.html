1. Core vision

The goal is not only a code demo. The goal is to imagine an autonomy stack where a trained mission-specific foundation model is placed close to the drone, on the companion computer / edge device. The GCS gives mission intent, the edge model understands the local scene and tactical context, and the flight controller executes safe low-level flight.

Mission intent
  → GCS / operator
  → drone companion computer
  → mission-specific foundation model
  → perception + reasoning + task decision
  → MAVLink command
  → flight controller / ArduPilot
  → motors and vehicle motion

3. Putting the foundation model at the edge

A general cloud model understands broad concepts. A drone mission needs a smaller, mission-specific model that is tuned or distilled for the operational domain: aerial scenes, tactical assets, navigation constraints, mission rules, and safety constraints.

Input

Local observations

Drone camera, depth/LiDAR if available, GPS, attitude, altitude, map context, team status, and mission objective.

Understanding

Scene semantics

Road, building, tree, open area, vehicle, person, landing zone, obstacle, friendly asset, unknown asset, hostile asset.

Reasoning

Mission decision

Inspect area, follow road, hold position, avoid obstacle, track asset, hand off target, ask GCS confirmation, or retreat.

Output

Safe command

High-level waypoint, velocity, loiter, land, RTL, or task update. The model should not directly control motors.

Design principle: the foundation model reasons about mission and scene. The flight controller remains responsible for low-level stabilization, arming rules, failsafes, and motor control.

4. Aerial scene understanding example

From a top-down drone camera view, the edge model should infer useful structure rather than just pixels:

Road geometry

Main road, side road, intersection, lane direction, stop lines, crosswalk-like markings, and drivable space.

Static world

Buildings, roofs, parking area, sidewalks, trees, vegetation, road boundaries, and open areas.

Dynamic assets

Vehicles on the road or parked near the road. In a mission setting these become trackable objects.

Mission meaning

Where can a drone observe? Where is occlusion? Which road segment or asset needs inspection?

5. Belief state from the drone

The edge model should not only detect objects. It should maintain a belief state: a structured, uncertain understanding of the world built from current sensor observations, prior map knowledge, and mission context.

Drone observation at time t
  camera_frame: aerial intersection
  pose_estimate: altitude + heading + GPS/local position
  mission_context: inspect road junction and identify assets

BeliefState(t):
  static_map:
    road_corridor_vertical:    confidence 0.94
    cross_road:                confidence 0.88
    intersection_center:       confidence 0.91
    buildings_or_roofs:        confidence 0.86
    trees_or_vegetation:       confidence 0.93
    parking_or_open_area:      confidence 0.78

  dynamic_objects:
    vehicle_1: class=car, state=parked_or_slow, confidence 0.82
    vehicle_2: class=car, state=parked,         confidence 0.76
    unknown_asset_region: near_intersection,    confidence 0.55

  tactical_labels:
    friendly_assets: none_confirmed
    enemy_assets:    none_confirmed
    unknown_assets:  vehicles require classification
    occluded_zones:  tree-covered road edges

  recommended_next_action:
    move_to_observation_waypoint
    look_down_at_intersection
    classify vehicles before assigning threat label
    report semantic map to GCS
What is known

Road structure, intersection geometry, trees, buildings, open areas, and visible vehicles.

What is uncertain

Vehicle intent, friendly/enemy identity, occluded regions under trees, and whether a road segment is blocked.

What the model should do

Ask for more observation, change viewpoint, classify assets, update the semantic map, and send a safe high-level command.

Pixels are not enough.
The drone needs:
  perception  → what objects are visible?
  geometry    → where are they in the local map?
  belief      → how confident are we?
  mission     → what matters now?
  action      → what should the drone do next?

8. Safety boundary

The autonomy model should not replace the flight controller. The safe split is:

Foundation model

Understands scene, mission, assets, risk, and intent. Produces high-level task or waypoint suggestions.

Companion computer

Runs model, checks local rules, communicates with GCS, sends safe MAVLink commands.

Flight controller

Handles arming, modes, stabilization, failsafes, landing, RTL, and motor outputs.
